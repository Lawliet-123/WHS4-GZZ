# 기능별 실행 상태표

12개 기능과 직접 메모리 접근 관측의 미구현 상태를 13개 행으로 출력한다.
누락된 기록을 정상으로 바꾸지 않는다. 하이퍼바이저 기능은 보류했고 커널 접근 센서는 추가하지 않았다.

## 바로 사용

프로젝트 루트에서 기존 시험 로그에 대해 실행한다. 새 드라이버 빌드 없이 분석할 수 있다.

```powershell
python .\tools\summarize_run.py --raw .\runs\mecha_kernel_cheat_001\raw_events.jsonl --format table
```

기존 숫자 요약 JSON과 상태표를 함께 출력하려면:

```powershell
python .\tools\summarize_run.py --raw .\runs\mecha_kernel_cheat_001\raw_events.jsonl --format both
```

별도 파일 저장은 선택 사항이다. `--out`은 이미 존재하는 파일을 덮어쓰지 않으며 상위 폴더가 있어야 한다.

```powershell
python .\tools\summarize_run.py --raw .\runs\mecha_kernel_cheat_001\raw_events.jsonl --format table --out .\feature_status_001.md
python .\tools\summarize_run.py --raw .\runs\mecha_kernel_cheat_001\raw_events.jsonl --format json --out .\summary_001.json
```

기존 자동화와의 호환을 위해 옵션을 생략하면 종전처럼 JSON만 출력한다.
새 JSON에는 `feature_status`가 추가된다. 나머지 요약 필드는 유지한다.

## 새 수집 실행에서 자동 출력

새 `agent` 폴더와 `tools` 폴더를 함께 사용한다. 기존 실행 명령은 그대로다.
Ctrl+C 또는 수집 종료 시 콘솔에 상태표가 출력되고 실행 폴더에 다음 파일이 추가된다.

- `feature_status.md`: 사람이 읽는 기능별 표.
- `feature_status.json`: 상태표의 기계 판독 자료. 마지막 관측·성공 시각(UTC), 활성 여부, 세부 건수 포함.

강제 프로세스 종료/전원 차단처럼 정리 코드가 실행되지 않으면 자동 파일은 생성되지 않을 수 있다.
그 경우 남은 `raw_events.jsonl`을 요약 도구에 입력한다. 종료 기록 부재와 공백을 함께 표시한다.
수집 시작 전에 발생해 로그 파일 자체가 만들어지지 않은 오류는 이 표로 확인할 수 없다.

새 세션에는 코드 검사 주기당 개수, 진단 주기, 서명 검사 활성 여부가 기록된다.
매 목록 교차 검사에 `driver_cross_view_status`가 추가되며 일치/차이/판정 불가와 근거를 기록한다.
이 이벤트는 새 점수를 부여하거나 기존 불일치 판정 규칙을 바꾸지 않는다.

## 상태와 집계 해석

| 상태 | 의미 |
|---|---|
| 검사 완료 | 기록된 검사에서 필요한 결과가 확인됨. 세션 전체의 무결점 또는 치트 부재를 보증하지 않음 |
| 관측됨 | 사건형 센서의 기록이 있음. 사건이 없는 다른 종류의 콜백까지 정상이라고 보증하지 않음 |
| 기준 설정만 | 코드의 최초 기준값만 확보. 기존 기준과 비교한 성공은 없음 |
| 일부 실패/불완전 | 성공·기준 설정·변화 관측과 함께 실패/불완전도 있음 |
| 실패/불완전 | 성공 근거 없이 실패 또는 완료 근거 누락이 있음 |
| 변화·차이 관측 | 검사상 변화, 목록 차이, 모듈 밖 주소 또는 시험 콜백 미관측. 악성 확정 아님 |
| 미관측 | 해당 기능의 실행을 뒷받침하는 기록 없음 |
| 비활성 | 로그에 기록된 모드/설정에서 기능이 꺼져 있음 |
| 지원 안 됨 | 필요한 기능 비트가 없고 실행 기록도 없음 |
| 판정 불가 | 불충분한 결과 또는 비활성 설정과 관측 기록의 충돌 |
| 미구현 | 직접 커널 메모리 읽기·쓰기 관측 센서가 구현되지 않음 |

기록은 이벤트 수, 성공 검사/짝은 유효한 검사 묶음이나 짝지어진 핸들 작업 수다.
프로세스 생성 같은 사건에는 성공 검사 건수가 0이어도 관측 기록이 있을 수 있다.
실패한 OpenProcess 요청도 정상적으로 기록된 핸들 작업이면 센서 실패로 세지 않는다.
권한 제한 행은 활성 enforce 이벤트의 before/after 권한을 현재 제한 마스크와 비교한다.
실제로 권한이 제거된 횟수, 제외 대상(kernel/self) 횟수는 세부 항목으로 구분한다.

실패/불완전은 실패·불완전 결과 기록과 집계 검증 문제 수이며, 실패한 고유 드라이버 수가 아니다.
핸들의 누락/중복 쌍은 집계 불완전 문제 1건으로 표시하고 실제 미짝 개수는 details에 남긴다.
한 기록에서 변화와 검사 실패가 함께 나타날 수 있어 각 열의 합이 기록 수와 항상 같지는 않다.
기록된 마지막 성공 뒤 센서가 멈췄는지 실시간으로 보증하지 않는다. 시각과 세션 종료 여부를 함께 확인한다.
`session_complete`는 session_end 기록 유무이며 실행 성공을 뜻하지 않는다.

파일 행은 해시 수집, 서명 검사, 식별 정책을 분리해 읽는다.
해시 성공이 있어도 서명 `not_checked`를 검사 완료로 바꾸지 않는다.
서명 API가 반환한 비정상/미서명 상태도 별도 결과로 보관하며 곧바로 치트 판정하지 않는다.
JSON `subchecks`에서 서명 활성 여부와 정책 항목 수를 확인한다. 빈 정책은 식별 규칙 비활성이다.

## 기존 v0.2.1 / v0.2.2 로그의 한계

기존 로그에 없는 옵션을 임의로 추정하지 않는다. 예를 들어 코드 검사 기록이 없고 `code_per_cycle`도 없으면
비활성이라고 단정하지 않고 활성 여부 null/미관측으로 표시한다.
기존 목록은 기록된 AuxKlib→PSAPI→AuxKlib 묶음을 오프라인 재비교한다.
행의 근거에 **오프라인 재비교**라고 표시하며, 당시 수집기의 비교 완료 이벤트가 있었다고 주장하지 않는다.
새 로그의 명시적 비교 이벤트가 있으면 그것을 우선하며 재비교 결과와 중복 집계하지 않는다.
여러 세션을 합친 로그는 거부하므로 세션별로 실행한다.

## 제공된 실제 시험 로그 결과

`reports/current_case/feature_status.md`와 `.json`에 재분석 결과를 포함했다.

- 보호 대상 상태 조회 325회 일치.
- 프로세스 사건 82건, 게임 스레드 사건 24건.
- 핸들 pre/post 각각 3,119건, 3,119쌍. 실제 메모리 읽기 횟수는 아님.
- 권한 제한 비활성(observe).
- 커널 이미지 로드 1건, 목록 신규 항목 기록 181건. 게임 이미지 이벤트 0건.
- 함수 진입부와 자체 디스패치 각각 650회 유효한 비교.
- 모듈 코드 비교: 동일 1,292회, 기준 설정 1회, 실패 7회(`hal.dll`).
- 목록 교차 오프라인 재비교 325회 일치.
- 시스템 스레드 검사 41회, 누적 스레드 검사 8,477회, 밖 관측 0.
- 시험 핸들 콜백 observed 45회.
- 파일 해시 성공 179건, 실패 3건. 세 실패는 dump_dumpstorport.sys, dump_stornvme.sys, dump_dumpfve.sys 경로의 파일 없음.
- 서명 미검사 182건, 식별 정책 0개.
- 직접 메모리 접근 관측 미구현.

## 변경·검증 범위

`agent/feature_status.py`, 수집기 종료 처리, 목록 비교 상태 이벤트, 요약 CLI와 테스트를 추가했다.
커널 드라이버 소스는 v0.2.2와 동일하므로 이번 상태표 기능 때문에 다시 빌드할 필요는 없다.
단, v0.2.2에서 추가했던 호출 문맥 필드는 그 드라이버 버전이 있어야 기록된다.
검증은 오프라인 테스트와 기존 실제 로그 재분석이다. 새 수집기의 Windows VM 실시간 실행은 미검증이다.

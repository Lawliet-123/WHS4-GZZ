# KernelSentinel 0.2.1 — 커널 담당 독립 검증

팀의 유저모드 치트 탐지와 분리해 커널 상태를 수집하는 실행 모드를 추가했다.
0.2.1은 수집기 변경이다. 포함된 커널 드라이버는 0.2와 동일하고,
0.1/캐시 패치 사용자는 이 전체 패키지의 드라이버를 새로 빌드해야 한다.
Windows 빌드·실제 커널 치트 탐지 성공을 검증한 릴리스는 아니다.

## 담당 영역

| 대상 | 관측/판단 | 필요한 정답 자료 |
|---|---|---|
| 로드된 모듈 범위 밖에서 시작한 시스템 스레드 | 커널에서 PsIsSystemThread, 생성 시각, 시작 주소 확인. 전후 모듈 목록이 안정적이고 동일 스레드가 3회 연속 목록 밖이면 조사 이벤트 | 별도 디버거/덤프로 해당 스레드와 코드의 존재·주소 확인 |
| 로드된 커널 모듈의 실행 코드 변경 | 첫 성공 검사 이후 SHA-256 차이 | 어떤 모듈/영역이 언제 변경됐는지 독립적으로 확인 |
| 선택한 함수 진입부 / Sentinel 자체 IRP 포인터 변경 | 드라이버 시작 시 기준과 비교 | 원래 값, 변경 값, 시각 및 변경의 원인 |
| 드라이버 식별 | 로드/목록 + 사용자 정책의 이름/파일 해시 | 검사한 샘플 파일 SHA-256, 경로, 로드 시각 |

스레드의 현재 RIP나 스택은 검사하지 않는다. 정상 모듈 내부에서 메모리만
읽고 쓰는 커널 치트, 시작 주소 위장, 기존 스레드 재사용, 조회 목록 자체를
조작하는 샘플 등은 놓칠 수 있다. 이들은 미검증/관측 범위 밖으로 구분한다.
일반 드라이버를 발견했다는 사실, 서명이 없다는 사실, VM이라는 사실만으로
치트라고 판정하지 않는다. 기본 이름·해시 정책은 비어 있다.

## 빌드·적용

- 새 폴더에 전체 압축을 풀고 `KernelSentinel.sln`을 x64로 빌드한다.
- VM은 Windows 10 22H2 x64, 빌드 19045를 사용한다. 새 native 스레드 센서는
  다른 OS 빌드에서 비활성화된다. OS 내부 반환 ABI를 사용하는 연구 구현이다.
- 기존 수집기를 종료하고 관리자 PowerShell에서 `sc.exe stop KernelSentinel`로
  중지한 뒤 STOPPED를 확인한다. 새 SYS와 agent/scripts/tools 폴더를 복사한다.
  개인 config 및 기존 runs는 보존한다. 이미 0.2 SYS를 빌드해 사용했다면
  이번 변경 때문에 SYS를 재빌드할 필요는 없지만, 0.2의 검증 상태는 별개다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\scripts\Build.ps1"
```

VM 프로젝트 폴더에서 새 SYS 설치 후 RUNNING을 확인한다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\scripts\Install.ps1" -SysPath ".\KernelSentinel.sys"
```

## 게임 없이 커널 검사

관리자 PowerShell, 프로젝트 폴더에서 실행한다. 새 out 디렉터리를 사용한다.

```powershell
python -m agent.main watch --kernel-only --session-id kernel_normal_001 --out .\runs\kernel_normal_001 --interval 2 --code-per-cycle 4 --thread-interval 15
```

이 모드에서는 게임 PID 등록, 핸들 권한 제한, 게임 대상 OB 상태 점검을 하지
않는다. 드라이버 로드 알림, 모듈 교차 조회, 실행 코드/진입부/자체 포인터 검사,
커널 스레드 검사는 유지된다. 커널 드라이버가 수집한 일반 프로세스 이벤트는
Python에서 제외하고 제외 개수를 기록한다. 이벤트 큐 자체는 공유되므로
다른 이벤트로 인한 큐 손실도 coverage_gap으로 기록한다.

`--kernel-only`와 `--pid`는 동시에 사용할 수 없고 이 모드는 observe 전용이다.
게임을 지정하는 기존 `watch --pid ...`는 기존처럼 OB 상태 점검도 수행한다.
커널 전용 모드의 callback_health가 비어 있는 것은 의도적으로 비활성화된
결과이며, 콜백이 정상 또는 고장이라는 증거가 아니다.

Ctrl+C로 종료 후 요약:

```powershell
python .\tools\summarize_run.py --raw .\runs\kernel_normal_001\raw_events.jsonl
```

## 실험을 성공으로 판단하는 기준

1. 정상 세션: thread_snapshots 및 thread_checks_not_unique_threads가 증가하고,
   상태·개별 조회 실패·coverage_gap을 확인한다. 경고 0건만으로 성공 판정하지 않는다.
2. 허가된 커널 샘플 세션: 샘플 해시/OS/SYS 해시, 실행·종료 시각, 독립적으로
   확인한 기대 흔적을 기록한다. 정상 세션과 out 디렉터리를 분리한다.
3. 기대 흔적이 실제로 존재할 때 센서 이벤트와 시간상 대응하는지 확인한다.
   지속성 조건은 기본 15초 간격 3회이므로 최초 관찰 후 최소 약 30초이며
   모듈 변동·처리 시간으로 지연될 수 있다.
4. 성공, 흔적이 있었으나 미탐, 관측 범위 밖, 검사 실패, 정상 변화/오탐을
   구분해 팀 공통 이벤트와 보고서에 남긴다. 커널 센서는 머신 전체 범위이므로
   player_id만으로 특정 원격 플레이어의 치트라고 단정하지 않는다.

실제 커널 샘플이 없는 경우의 결과는 "커널 센서 구현 및 정상 동작 검증"이다.
합성 로그 테스트를 "실제 커널 치트 탐지"로 집계하지 않는다.

## 참조와 검증

Darken의 커널 스레드 시작 주소 수집 및 ac의 스레드/디스패치 검사 방향은
`PATCH_v0.2.md`에 검토 소스와 commit을 명시했다. 이번 모드 추가에서 해당
프로젝트 코드를 복사하지 않았다. 커널 드라이버 소스는 저장된 0.2와 바이트 단위로 같다.

오프라인 회귀 42개 통과. 새 통합 검사는 API 대역으로 커널 전용 3회 순회,
모듈 밖 주소의 지속성 판정 전달, 게임 접근/heartbeat/OB probe 미실행,
유저 이벤트 제외, 기존 게임 대상 확인, 상충 옵션 거부를 검증한다.
Windows WDK 빌드, VM 로드, 실제 커널 샘플, Driver Verifier, CPU 부하는 미검증이다.


## 2026-09-27 빌드 호환성 수정
`driver/thread_scan.h`에 `THREAD_QUERY_INFORMATION`이 정의되지 않은 경우에만
문서화된 값 `0x0040UL`을 정의하도록 추가했다. 이전의 드라이버 바이트 동일 설명은
이 수정 전 상태를 가리킨다. 테스트 대역의 매크로 정의를 제거해 누락 조건으로
42개 오프라인 테스트를 다시 통과했다. Windows WDK 빌드는 여전히 미실시다.

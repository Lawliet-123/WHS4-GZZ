# 확인할 부분과 다음 승인 사항

2026-10-04. 1차 관측·기록만 구현했다. 아래 후속 제안은 아직 적용하지 않았다.

## 구현에 반영한 안전 처리

- API 호출 성공과 실제 연결 여부 분리.
- PID+생성 시각 검증, 이미 종료된 프로세스와 접근 거부 구분.
- 등록부 오류를 자기 검사 성공으로 덮지 않음.
- restartable=False인 탐지기와 실행 중 ONESHOT도 조회. 재시작 권한과 검사 범위를 분리.
- 7필드·raw_score=0 유지. 정상 회차도 기록.
- Windows 생성 시각은 문자열로 출력해 Dashboard의 64비트 정밀도 손실 방지.
- argv·키·임의 예외 메시지는 전송하지 않음.
- 차단·종료·디버거 해제 없음. 테스트 도구의 자식 프로세스 정리와 운영 기능을 분리.

## 런처 담당자에게 확인할 부분

1. 배포 대상 Launcher가 README에 적힌 등록부 필드·생성 시각 단위를 유지하는지. 10/6 main 31dc8332a770f51f2f50856637dcf8a1a4cee102 사본까지 확인했으며 후속 변경이 있으면 재검사가 필요하다.
2. selfdefense_anti_debug를 별도 상주 모듈로 등록할지. 같은 프로세스에 통합한다면 sender 소유권과 실행 방식을 다시 맞춰야 한다.
3. 자기 프로세스가 멈추면 스스로 보고할 수 없으므로 기존 런처/워치독 재시작 정책으로 복구되는지.
4. 세 모듈의 공통 session/player/t0, 각자의 출력 경로·outbox가 올바르게 전달되는지.

## 팀 전체가 참고할 부분

LocalGuard/KernelWatcher 담당: anti_debug는 등록된 안티치트 PID를 QUERY_INFORMATION | SYNCHRONIZE로 조회한다. 이 접근을 자체 공격으로 오인하는지 확인한다. 예외가 필요하면 이름만으로 허용하지 말고 등록부의 PID+생성 시각과 요청 권한을 함께 확인하는 방식을 협의한다. 이번에 다른 모듈의 규칙은 수정하지 않았다.

Dashboard/scoring 담당: module=selfdefense, evidence.kind=debugger_presence인 운영 이벤트다. raw_score=0이어도 status=DETECTED/ERROR를 표시해야 한다. 정상 개발 중 디버거 연결도 DETECTED이며 악성 여부를 자동 확정하지 않는다. scope·scan_complete·registry_state·개별 대상 state를 함께 본다. EXITED는 연결 없음이 아니라 검사 대상 종료다.

릴리스 담당: anti_debug와 런처 변경을 포함한 최종 배포 파일이 확정된 뒤 integrity 기준·pin을 만든다. 기준 파일을 매 시작 때 자동 갱신하지 않는다.

## 추가 승인 후 할 수 있는 개선

1. 등록부에 기대 모듈 목록·schema_version 추가: entries에서 누락된 탐지기까지 판단하려면 런처와 계약이 필요하다. 현재는 등록된 대상만 감시한다.
2. 검사 주기·로그 보관: 현재 검사 후 2초 대기, 매 회차 기록. 실측 후 주기와 회전·보관 기간을 결정한다.
3. Python 수준 디버깅 관측: 각 Python 프로세스 내부 계측이 필요할 수 있어 이번 외부 네이티브 검사와 별도 설계한다. 정상 profiler·coverage와의 구분도 필요하다.
4. 중복 PID 관측 정리: 현재 등록 이름별로 기록한다. 여러 별칭이 같은 프로세스를 가리키면 합쳐서 표현할지 소비 측과 정한다.
5. 2차 대응: 경고·게임 시작 보류·재검사 후 허용 정책을 런처에서 구현할지 결정한다. 개발 모드, 검사 실패 시 처리, 실행 중 게임 처리와 사용자 안내를 먼저 정한다. 디버거/타 프로그램 강제 종료는 제안 범위에 넣지 않았다.

하트비트·커널 검사·강제 차단은 이번 구현에 추가하지 않았다.
